# Beluga: commands, mentions and skills

Design, 2026-11-11. Builds on `2026-11-11-beluga-desktop-design.md` (the parent design) and on the shipped chat app (version 0.1.1). Where the two disagree, this document wins for the features it covers.

Items marked **(owner)** were stated or approved by the product owner. Items marked **(my call)** were decided by the designer and can be overturned.

## Intent

The owner opened the shipped app, typed `/` and `@`, and nothing happened. They want the working habits they know from Claude's tools: a `/` menu of commands and skills, `@` to pull in files, a place to see and add skills, and the skill packs already there when the app is installed. **(owner)**

This step makes skills real in the app that exists today, which can chat but cannot yet edit files or run commands. It is honest about that limit instead of hiding it.

## Goals

1. Typing `/` in the message box opens one list of the app's commands and the user's switched-on skills, each with a description; typing filters; Enter runs. **(owner, from their screenshot and the approved mockup)**
2. Typing `@` lists files from a folder the user opened and attaches the chosen file. **(owner)**
3. A Skills screen shows everything installed, grouped by pack, with a switch per pack and per skill, and lets the user add their own. **(owner)**
4. The researched skill packs ship inside the installer, so they are present the moment the app is installed. **(owner: "find all the skills and plugins and add them with the installed version")**
5. Chat habits from the reference tools: edit and resend, type while it replies, Esc to stop, and a meter for how full the chat is. **(owner approved the list)**

## Non-goals (this step)

- The agent editing files, running commands, or using tools of any kind. That is the next step (the parent design's project-work stage). **(my call, owner told)**
- Skills switching themselves on. Here a skill runs when the user picks it. Letting the model choose a skill needs tool calls and an extra request per use, which matters at 50 free requests a day. **(my call)**
- Plugin parts that are not skills: hooks, sub-agents, slash-command files, MCP servers, installers. Packs are loaded for their skills only. **(my call, consistent with the parent design)**
- Automatic pack updates, the skills.sh search feed, permission modes, file-change review, rewind, shell mode, background agents, a side preview panel, connectors, scheduled tasks, voice. All later. **(owner approved the split)**

## Anti-goals

- A skill list that looks ready but silently cannot do what it says. Every skill that expects to act on the computer says so before the user runs it.
- Copying Anthropic's names, wording or look. Interaction patterns only.
- The app reaching the network for anything the user did not ask for. Installing a pack from GitHub is user-initiated and is the only new network use.
- Running any script that came inside a skill pack.

## How skills reach the user

**Shipped inside the installer (15 packs).** `superpowers`, `agent-skills`, `anthropic`, `emil`, `engineer`, `gstack`, `ecc`, `mattpocock`, `impeccable`, `ui-ux-pro-max`, `expo`, `react-native`, `apollo`, `astral`, `agents`. **(owner asked for all installed; the selection of which can legally and sensibly ship is my call)**

**One click in the Skills screen, downloaded from GitHub at the pinned commit (3 packs).** **(my call)**

| Pack | Why it is not inside the installer |
|---|---|
| `claude-red` | Offensive security. The owner agreed it sits behind a warning. Keeping it out of the installer also avoids antivirus flags on the app itself. |
| `vercel` | The repository has no license file, so there is no license text to redistribute. Downloading it from its own repository on the user's request is the user obtaining it, not us redistributing it. |
| `trailofbits` | CC-BY-SA-4.0 is a share-alike license. Shipping it unmodified beside MIT code is probably fine as a collection, but this has not had a legal read, so it is fetched from its own repository instead. If the owner gets a legal yes, it moves into the installer. |

**What is copied from each pack.** Only text a chat can use: each skill's `SKILL.md`, and other `.md`, `.txt`, `.json`, `.yaml`, `.yml`, `.csv` files in the skill folder up to 256 KB each; plus the pack's `LICENSE*`, `NOTICE*`, `THIRD_PARTY_NOTICES*` and, for `gstack`, `licenses/`. Scripts, binaries, fonts and images are left out for now, which is why the installer grows by megabytes, not tens of megabytes. Files are copied byte-for-byte; nothing inside a pack is edited. **(my call)**

**Where they live in the repository.** Vendored under `src-tauri/resources/skills/<pack-id>/`, committed, with a lock file `skills.lock.json` at the repository root recording, per pack: repository, full commit, selection rule, license, and a checksum of the copied tree. A fetch script regenerates the vendored tree from the lock file. Vendoring keeps builds offline and reproducible and puts the licenses under review in the repository. **(my call)**

**Licenses.** Every pack's license and notice files ship with it. The Skills screen shows each pack's license, and each skill's own `license:` where it declares one (ECC has mixed ones). An "Open-source licenses" entry in Settings lists every pack with its license text.

## The skill model

- A **pack** is a group of skills from one source. Bundled packs are read-only. User-added skills live in a pack called "Added by you".
- A **skill id** is `pack:name` (for example `superpowers:brainstorming`), and plain `name` for "Added by you". Ids are what the `/` menu shows and what is stored.
- **Name** comes from frontmatter, falling back to the folder name. **Description** comes from frontmatter, falling back to the first sentence of the "Description"/"Metadata" section or the first paragraph, cut at 200 characters. A skill with no usable `SKILL.md` is listed as broken with the reason, never silently dropped.
- Each skill has a **switch**. A pack switch turns all of its skills off without forgetting their individual settings.
- Each skill carries an **acts-on-your-computer** mark, decided at fetch time by the text scan and stored in the lock data, with a hand-kept override list for wrong guesses. Such a skill shows the note: "Written for an agent that can edit files and run commands. In chat it can guide you step by step, but it cannot act yet." It can still be run.

**On by default (my call).** At most 40 skills, so the `/` menu is useful on day one. All of `superpowers` except the three that are only about dispatching helpers and worktrees; `anthropic:frontend-design`; and the builder's pick, from `agent-skills`, `emil`, `engineer` and `mattpocock`, of the best one skill each for: writing a spec, test-first work, debugging, code review, refactoring, git and pull requests, documentation, UI polish and animation, and the five most common stacks (React, TypeScript, Python, Node, Rust). Where two packs cover the same job, `superpowers` wins. Everything else is installed and off. The exact list is written into a `default-skills.json` and shown to the owner in the hand-over.

## Running a skill

A skill is run by picking it from the `/` menu, optionally followed by text: `/superpowers:brainstorming a login page`. **(my call: explicit only in this step)**

What happens:

1. The skill becomes **active for this chat**. Active skills are stored with the chat and shown as chips above the message box ("superpowers:brainstorming ×"). Removing the chip deactivates it from the next message on.
2. On every request in that chat, the app sends, ahead of the conversation: a short fixed note about where the model is running, then each active skill's `SKILL.md` body, in the order they were activated.
3. The text after the skill name, if any, is sent as the user's message. With no text, the app sends the message "Start." so the skill begins. **(my call)**
4. The thread shows a quiet line where the skill was activated: "Using superpowers:brainstorming".

The fixed note, exact:

> You are running inside a chat app. You cannot read or change files, run commands, browse, or start helpers. When the instructions below tell you to do any of those, say what you would do and ask the user to do it and paste the result, or work from the files they attach. Do not claim to have done something you cannot do.

Limits: at most three active skills per chat; a skill body over 60,000 characters is refused with a plain message. The context meter (below) counts active skills. A skill's other files (references, examples) are not sent automatically; the skill detail view lists them and each has an "Attach to this chat" action. **(my call)**

## The `/` menu

Matches the approved mockup (`docs/superpowers/mockups/commands-and-skills.html`). **(owner saw it)**

- Opens when `/` is the first character of the message box. Closes on Esc, on deleting the `/`, or on clicking away.
- Two groups: Commands, then Skills. Each row: name, one-line description, source (the app's name, the pack id, or "Added by you").
- Typing filters both groups by name, matching from the start of the name or of any word in it (words split on `:`, `-`, `_`), then by description words. Up and Down move, Enter runs the highlighted row, Tab completes the name into the box without running it.
- If nothing matches, Enter sends the text as an ordinary message.
- A footer link "Manage skills" opens the Skills screen.

Commands in this step:

| Command | Does |
|---|---|
| `/new` | Starts a new chat |
| `/model` | Opens the model picker |
| `/skills` | Opens the Skills screen |
| `/usage` | Shows free requests left, this chat's requests and cost, and this month's spend |
| `/compact` | Shortens this chat (below) |
| `/export` | Saves this chat as a Markdown file through a save dialog |
| `/settings` | Opens Settings |
| `/help` | Lists the commands and the keyboard shortcuts |

`/compact`: asks the current model, in one request, to summarise the conversation so far (the request says so in the confirmation: "This uses one request."). On success the earlier messages stay visible in the thread under a divider "Summarised above this line" but are no longer sent; the summary is sent in their place. Compacting a chat with fewer than four messages is refused with a plain message. An optional text after the command ("/compact keep the database decisions") is passed as what to preserve.

## The `@` menu

- A chat can have one **folder** attached. "Open a folder" lives in the sidebar and in the `@` menu when no folder is set. The folder is chosen through the system folder dialog and remembered per chat; new chats start with the last folder used.
- Typing `@` anywhere in the message box (at the start or after a space) opens a list of files and folders inside it; typing filters by path; Enter attaches.
- Attaching a file adds it as an attachment chip, exactly as the existing Attach button does, with the same limits (five attachments, 200 KB of text each, images only for models that read them). The `@word` text is removed from the box.
- Attaching a folder attaches a text listing of its files (names and sizes, up to 500 entries), not their contents.
- Listing respects `.gitignore`, skips hidden folders, `node_modules`, `target`, `dist`, `build` and `.git`, and stops at 5,000 files with a note that the list is cut.
- The app only reads. It never reads outside the chosen folder: paths are resolved and checked, and links that point outside are skipped.
- With no folder set, `@` offers one row: "Open a folder to mention its files".

## The Skills screen

Matches the mockup. Reached from the sidebar, `/skills`, and the `/` menu footer.

- **Installed tab.** One card per pack: name, skill count and how many are on, license, "built in" or where it came from, and a pack switch. Expanding a card lists its skills with their descriptions and switches. A search field filters across all packs. The header says how many skills are on.
- **Skill detail.** Opening a skill shows its rendered `SKILL.md`, its pack, license, source link (the repository at the pinned commit), the acts-on-your-computer note if it applies, its other files with "Attach to this chat", and a "Use in this chat" button.
- **Add a skill.** Three ways: a folder containing `SKILL.md`; a ZIP of such a folder; a GitHub link to a repository or to a folder in one. The app validates (a `SKILL.md` exists, name and description can be found, total text under 2 MB, no more than 200 skills in one add), shows what it found, and copies the text files into the app's data folder. Skills added this way can be removed. Scripts are not copied.
- **More packs tab.** Lists `claude-red`, `vercel` and `trailofbits` with what each is, its license, its size and an Install button, plus "Install from a GitHub link". Installing downloads the repository archive at the pinned commit from GitHub, checks it against the recorded checksum, and copies text files as above. Installed extra packs can be removed.
- **claude-red warning.** Before install, a dialog with exact copy: heading "This pack is for authorised security testing"; body "Claude-Red contains offensive security techniques. Use it only on systems you own or have written permission to test. Many models will refuse parts of it. It installs switched off."; buttons "Install, switched off" and "Cancel". Its skills are off after install and each must be switched on by hand.

Network: installing from GitHub contacts `github.com`, `codeload.github.com` and `api.github.com`, and only when the user presses Install or Add. The README's privacy section is updated to say so.

## Chat habits

- **Edit and resend.** A pencil on the user's most recent message puts its text back in the message box. Sending replaces that message and everything after it. Only the latest user message can be edited; there are no branches. **(my call: simplest form)**
- **Type while it replies.** The message box stays usable during a reply. Sending queues one message, shown above the box as "Queued: …" with a remove button; it is sent when the reply ends. A second send replaces the queued one.
- **Esc** stops the current reply (same as the Stop button) when the `/` or `@` menu is not open.
- **How full the chat is.** The header shows "Chat is 12% full", an estimate from the characters that would be sent (messages, attachments, active skills) divided by four, against the model's context length. From 70% it turns amber and adds "Use /compact to shorten it". Above 100% sending is still allowed; the existing "chat is too long" error covers the failure.

## Constraints carried over

All of the parent design's and Plan 1's global constraints still hold: the key never reaches the interface; no telemetry; no hard-coded model names; the working name in its three allowed places; bundled fonts; inline SVG icons; the approved colour tokens; tests pass on macOS, Windows and Linux in CI; user-facing copy quoted here is exact.

New for this step:
- Nothing inside a skill pack is executed, by the app or by its build and fetch scripts.
- Vendored pack files are copied byte-for-byte and never edited.
- File reading for `@` goes through the Rust core, which enforces the folder boundary.

## Decisions added after builder review (all my call)

**A skill that is too long for the model.** The 60,000-character refusal stays. In addition, when a skill is run, the app estimates the characters of the fixed note plus all active skill bodies, divided by four. If that is more than half the current model's context length, the skill is not activated and the user sees: "This skill is too long for {model name}. Pick a model with a larger limit, or remove another active skill." The same check runs when the model is changed with skills active; skills that no longer fit stay on their chips but are marked "too long for this model" and are not sent.

**Running a skill sends a request.** Picking `/skill` sends immediately and uses one request like any message, with "Start." stored as a real user message when no text is given. The `/` menu footer says "Running a skill sends a message".

**What is stored, and the database change.** The store gains a migration step (schema version 2; version 1 databases from 0.1.x are upgraded in place and keep their chats). Chats gain: the list of active skill ids, the folder path, the compaction summary, and the id of the first message still sent after compaction. Messages gain a `kind`: `message` or `note`. "Using superpowers:brainstorming" lines are `note` rows; notes are shown and exported but never sent to the model. What is sent is: the fixed note and active skill bodies when any skill is active, then the compaction summary as a system message beginning "Summary of the earlier conversation:" when there is one, then every `message` row from the boundary on.

**Edit and resend with skills.** Active skills are chat state, not part of a message, so editing a message leaves them active. Rows after the edited message, including notes, are deleted. If the edited message was typed as `/skill some text`, only "some text" returns to the box. "Start." can be edited like any message.

**Compacting with skills.** The summary request contains the conversation only, not the skill bodies. Skills stay active afterwards. `/compact` uses the current model. If the conversation does not fit, the newest messages that fit in 60% of the model's context are summarised and older ones are dropped from what is sent, with the note "The oldest messages were too long to include in the summary." A failed summary changes nothing and shows the existing error.

**The acts-on-your-computer mark and the default list.** Every default-on skill is read by a person-equivalent pass (the builder reads its `SKILL.md`) and its mark set by hand. All other skills keep the scan's result. `mattpocock` is 31 skills after leaving out `in-progress`. The first vendoring uses exactly the commits in the table above.

**Size ceiling.** The vendored tree may be at most 25 MB on disk and may add at most 8 MB to any installer. If it is over, `.json` and `.csv` files are dropped first (keeping `.md` and `.txt`), and the builder reports what was dropped.

**Awkward files.** Symbolic links are skipped. A file whose path inside the vendored tree would be longer than 180 characters is skipped. Both are listed in the lock file. "Byte-for-byte" applies to the files that are copied.
